# 团队功能需求文档（Team）

> 状态：设计稿 · 最后更新：2026-10-01
> 范围：平台用户之间的团队组织、工作区受控共享、跨用户工作区调用
> 相关：`docs/requirements.md`（系统总体规格）

## 1. 背景与目标

当前一个用户只能查看、调用自己名下的工作区。团队功能让用户把自己的工作区**以"工具"的形式**借给队友调用：

- **组织层面**：用户可创建团队、加入多个团队、在多个团队中担任队长；队长负责邀请/审批/踢人，可移交队长。
- **共享层面**：工作区属主可把工作区共享给若干团队；团队成员可对该工作区发起 `a2a_call`，只拿最终答复。
- **隔离层面**：共享仅授予"调用权"，**不授予"可见权"**——调用方看不到被执行工作区的监控、思考、工具调用、产物、简报与调用细节。

## 2. 角色与名词

| 名词 | 含义 |
|---|---|
| 团队（Team） | 由一名队长（owner）与若干成员组成的协作单元 |
| 队长（leader） | 团队的 `owner_id`，唯一真源；拥有邀请/审批/踢人/移交/改名/解散权限 |
| 成员（member） | 活跃加入团队的用户 |
| 属主（workspace owner） | 工作区的创建者，唯一可共享/取消共享该工作区的人 |
| 调用方（caller） | 发起 `a2a_call` 的团队成员及其工作区（记为 A） |
| 执行方（target） | 被调用的共享工作区（记为 B）及其属主 |

## 3. 核心原则

1. **调用权 ≠ 可见权**。共享只放宽"能否对该工作区派任务"，**不放宽**监控订阅、Nexus 时间线、产物、调用记录列表的属主校验。
2. **执行方属主是通知归属**。共享工作区产生的简报、权限/提问卡、监控只发给**属主**，绝不发给调用方或团队成员。
3. **调用方只拿最终答复**。调用方不会收到 thinking / tool call / 监控轮细节，仅通过 `a2a_task`（或完成提醒）取得最终结果。
4. **一个工作区可共享到多个团队**；一个用户可同时创建/加入多个团队。

## 4. 团队生命周期

### 4.1 创建
- 任意用户可创建团队，创建者即队长（`Team.owner_id`）。
- 创建时校验：创建者当前"创建数"未超过上限（见 §6）。
- 团队名全局唯一。

### 4.2 邀请（队长 → 用户）
- 队长按用户名邀请已注册用户。
- 生成一条 `pending` 成员记录，`kind=invite`、`initiated_by=队长`。
- 被邀请人接受后转为 `active`；可拒绝（删除该记录）。
- 接受时校验被邀请人"加入总数"未超上限。

### 4.3 申请加入（用户 → 团队）
- 用户可申请加入某团队。
- 生成一条 `pending` 成员记录，`kind=request`、`initiated_by=申请人`。
- 队长审批：通过转 `active`，拒绝则删除。
- `join_policy` 预留 `open`（无需审批直接加入）/`closed`（禁止申请），v1 默认 `approval`。

### 4.4 踢人 / 退出
- 队长可移除任意成员。
- 普通成员可自行退出。
- **队长不能直接退出**：须先移交队长或解散团队。
- 成员退出/被移除时，自动清理其共享给该团队的 `TeamWorkspace` 记录。

### 4.5 移交队长
- 队长可将队长身份移交给任一活跃成员，`Team.owner_id` 更新。

### 4.6 解散
- 仅队长可解散团队；级联删除成员关系与共享关系。

## 5. 工作区共享

- 仅工作区**属主**可共享/取消共享。
- 只能共享到**自己已加入**的团队（活跃成员）。
- 支持一次选择共享到多个团队（多对多）。
- 共享开关以团队为粒度：同一工作区可同时共享给团队 T1、T2，也可随时取消其一。
- **共享 ≠ 转移**：工作区仍归属属主，团队只获得调用权。

## 6. 数量限制（可配置）

为防止滥用与资源失控，对每个用户的团队数量设上限。所有限制通过 `server/config.py` 读取，环境变量优先于根 `.env`：

| 配置项 | 默认 | 含义 | 强制点 |
|---|---|---|---|
| `AGENT_SWARM_TEAM_MAX_OWNED` | `3` | 一个用户最多**创建**（担任队长）的团队数 | 创建团队时 |
| `AGENT_SWARM_TEAM_MAX_JOINED` | `8` | 一个用户最多**活跃加入**的团队总数（含自己创建的团队） | 申请加入、接受邀请、审批通过时 |
| `AGENT_SWARM_TEAM_MAX_MEMBERS` | `50` | 单个团队的活跃成员上限 | 邀请接受 / 审批通过时 |
| `AGENT_SWARM_TEAM_MAX_PENDING` | `10` | 一个用户同时挂起的待处理邀请/申请条数（防刷） | 邀请/申请创建时 |

计数口径：
- **创建数** = `teams.owner_id == user` 的行数。
- **加入数** = 该用户 `status=active` 的成员关系数（**包含**其作为队长的团队）。
- 达到上限时接口返回明确的 4xx 错误与文案（如"你创建的团队已达上限（3）"）。
- 并发安全：在写库前于同一事务/短会话内复查上限，避免并发绕过。

## 7. 访问控制矩阵

| 能力 | 工作区属主 | 共享团队活跃成员 | 其他用户 |
|---|---|---|---|
| 工作区管理 / 详情（path / notes / purpose） | ✅ | ❌ | ❌ |
| Nexus 订阅 · 监控时间线 · 历史回放 | ✅ | ❌ | ❌ |
| 产物页 | ✅ | ❌ | ❌ |
| 简报 / 权限卡 / 提问（飞书 · 微信 · web） | ✅ | ❌ | ❌ |
| `a2a_call` 派任务 | —（禁止自调） | ✅ | ❌ |
| `a2a_task` 取结果 | ✅ | ✅（仅自身发起的） | ❌ |
| 调用记录（指令 + 答复） | ✅（执行视角） | ✅（发起视角） | ❌ |

## 8. 跨用户调用流程

1. 调用方 A（某团队成员）通过 MCP `list_workspaces` 发现被共享的工作区 B，可见字段：`name / purpose / capabilities / agent_type / status / owner`（**不含** path、notes、session、调用记录）。
2. A 调 `a2a_call(target=B, message=…, from_workspace=A)`；服务端校验 B 是否共享给 A 所在的活跃团队。
3. 任务落库并以 B 的插件执行；**执行会话沿用前台优先**（属主在 TUI 可见；任务轮不进监控管道）。
4. A 通过 `a2a_task` 轮询或完成提醒取得最终答复。
5. 双方均可在各自「调用记录」页看到该条记录（**指令 + 答复**，不含思考/工具细节）。

## 9. 通知与权限路由（隔离要求）

- 共享工作区产生的一切推送（完成简报、权限请求、提问、产物推送）**只发给执行方属主**，绝不发给调用方或团队成员。
- 权限/提问由执行方属主应答，调用方不参与、收不到卡片。
- 调用方若中途放弃等待，沿用现有"长任务完成提醒"机制回到 A 的工作区。

## 10. 数据模型

```
Team           + join_policy: approval|open|closed（默认 approval）
               + description?
TeamMember     + status: pending|active
               + kind: invite|request
               + initiated_by: user_id
               + created_at
TeamWorkspace   id, team_id, workspace_id, shared_by, created_at
               UNIQUE(team_id, workspace_id)
A2aTask        + from_user_id: str = ""   # 调用方用户（跨用户取件授权）
```

- 队长身份以 `Team.owner_id` 为准，成员表不重复存 role。
- 旧字段 `Workspace.team_id`（单团队外键）**弃用保留**，共享关系一律走 `TeamWorkspace`。
- `init_db` 自迁移加列，不删表。

## 11. 接口概要

### 11.1 团队 REST（新增 `server/api/teams.py`）
- `GET/POST /api/teams`；`GET/PATCH/DELETE /api/teams/{id}`
- `POST /api/teams/{id}/members/invite {username}`（队长）
- `POST /api/teams/{id}/join`；`POST /api/teams/{id}/members/{uid}/approve|reject`
- `DELETE /api/teams/{id}/members/{uid}`（踢人）；`POST /api/teams/{id}/leave`
- `POST /api/teams/{id}/members/{uid}/transfer`
- `GET /api/teams/invitations`（我的待处理）

### 11.2 工作区共享
- `PUT /api/workspaces/{wid}/shares {team_ids:[…]}`（整体替换，仅属主）
- `GET /api/workspaces/{wid}/shares`

### 11.3 MCP
- `list_workspaces`：并入共享给我的工作区（带 `shared` 标记，字段见 §8 第 1 点）
- `a2a_call`：目标可见性放宽到共享工作区；写行 `user_id=执行方属主`、`from_user_id=调用方`
- `a2a_task`：授权 `user_id==我 OR from_user_id==我`

### 11.4 调用记录
- `list_calls` 过滤扩为 `workspace_id==wid OR from_workspace_id==wid`
- `delete_call` 属主为执行方或发起方均可删

## 12. 前端（`web/src/App.tsx`）

- 顶栏新增「团队」页：我的团队列表 / 创建；详情含成员、待审批、共享工作区；邀请（用户名）、审批、踢人、移交、退出；待办红点。
- 工作区页：每个工作区加「共享到团队」多选（仅属主，列出我所在的团队）。
- **不做**共享工作区的展示/派发 UI：成员只通过 MCP 发现与调用（用户决策）。

## 13. 不做的事（范围外）

- 团队内的工作区对成员**不**开放监控/Nexus/产物/简报。
- 不提供网页端对共享工作区的调用入口。
- 团队不改变工作区归属；不做团队级计费/额度。
- 邀请不额外推送到飞书/微信（仅 web 团队页可见）。

## 14. 测试要点

- 数量限制：创建达上限、加入达上限、团队成员达上限、待处理达上限各自的拒绝路径。
- 共享可见性：仅属主可共享/取消；非成员不可共享到团队。
- 跨用户调用：A 能调 B、能取结果；非成员调用被拒。
- **隔离红线**：团队成员订阅 B 被拒、看不到 B 的产物与调用记录列表（除自身发起）、简报/权限卡只到属主。
- 调用记录：A、B 均可见（指令+答复），无监控细节。
- 生命周期：踢人/退出清理共享；队长不可直接退出；移交后权限正确。
